# MVP 测试记录

## 测试背景

团队曾在 Chrome / Safari 环境下，围绕“设置对局 → 圆桌记录 → 组队投票 → 任务结算 → 三胜结束”执行 21 条 MVP 测试用例。该记录是当时版本的历史快照，不等同于当前版本的自动化测试结果。

## 结果概览

- 用例总数：21
- 当时通过：16
- 当时记录为未通过或与文档不一致：5

## 当时发现的差异

| 用例 | 领域 | 当时观察到的结果 | 性质 |
| --- | --- | --- | --- |
| TC-02 | 阵容校验 | 修改特殊角色后没有警告，进入按钮仍可点击 | 功能缺失/规则校验 |
| TC-05 | 局内规则 | 只显示阵营角色能力，缺少开局流程、任务轮次和任务结算 | 内容缺失 |
| TC-08 | 队长标记 | 使用金色圆环和圆桌中央文字，而非预期的座位下方红字 | 规格与视觉实现差异 |
| TC-09 | 选中座位 | 选中态为深色而非文档预期的蓝色 | 规格与视觉实现差异 |
| TC-14 | 投票初始态 | 默认全员赞成，不存在“尚未投票”状态 | 交互模型差异 |

其余用例覆盖并通过了人数配置、规则页返回、笔记保留、队伍人数限制、第五轮处理、表决和否决记录、普通任务结算、8 人局第 4 个任务规则，以及蓝/红双方三次任务胜利后的结束流程。

## 如何理解这些结果

测试不仅是在找 Bug，也在检验需求是否写得足够清楚。上表同时包含三类发现：真正缺少的业务规则、内容不完整，以及实现与文字规格不同但未必影响可用性的设计差异。后续迭代应先判断用户目标是否受损，再决定修复代码还是更新规格。

## 后续建议

- 把稳定的规则判断补成自动化单元测试，尤其是人数/角色配置、连续否决、8 人局第 4 个任务和刺杀。
- 每次发布前至少走一遍核心端到端路径。
- 可用性测试应让目标用户独立完成任务，观察是否找得到入口、是否理解状态与下一步；不要只告诉用户如何操作后再验证。
- 新发现统一创建 GitHub Issue，记录环境、步骤、预期、实际结果和证据。

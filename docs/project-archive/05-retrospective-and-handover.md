# 项目复盘与维护交接

## 第一阶段结论

Avalon Companion 的学习型 MVP 已形成完整对局闭环，并积累了需求、实现、测试、部署和交接资料。因此可以将第一阶段视为结项：Linus 完成阶段负责人和 Product Owner 的验收/交接职责；仓库后续由 Yumi 作为维护负责人继续管理。

“阶段结项”不等于仓库冻结或产品永远完成。它表示原团队对这一阶段的目标、范围和责任有了明确终点；未来的概率分析、用户增长或商业化应被视为新的产品阶段，重新确定负责人、目标、范围与合作约定。

## 团队共同获得的能力

- 产品：从真实问题出发，把想法收敛为可交付的 MVP，并接受范围取舍。
- User-Centred Design：围绕线下玩家的情境设计流程，通过可用性测试和反馈继续修正。
- 敏捷协作：理解 Product Owner、Scrum Master、Developer、Backlog、评审和回顾之间的关系。
- 工程：使用 Next.js、React、TypeScript、GitHub Flow、代码评审、CI/CD 和响应式界面。
- 规则建模：把人数、角色、队长轮换、组队表决、任务结算、连续否决和刺杀转成状态与逻辑。
- 质量与交付：处理存档可靠性、安全性、构建/部署、文档、国际化、反馈入口与新手指引。
- 维护意识：区分历史规格和当前实现，并让没有原作者陪同的人也能接手。

## 推荐的下一阶段工作方式

对当前规模，使用轻量流程即可：

```text
用户反馈 / 想法
  → GitHub Issue
  → 维护者确认优先级
  → 分支与 Pull Request
  → Review + CI
  → 合并与部署
  → 收集下一轮反馈
```

- GitHub Issues / Projects：需求、Bug、Backlog 和公开决策的唯一事实来源。
- Discord 或团队可达的聊天工具：即时讨论；重要结论必须回写 Issue 或文档。
- 仓库 `docs/`：长期产品背景、测试、交接和部署知识，避免依赖即将停用的飞书组织。

## 飞书 CLI 智能体的定位

“圆桌骑士工坊 CLI”在飞书中显示为智能体，是这个自建应用的可见身份和对话入口。当前授权首先让维护工具能够代表用户读取和整理文档；它不会因为收到一句 `hi` 就自动理解并回复。

若未来继续使用飞书，可为它增加：

- 事件订阅：接收私聊、群聊或文档事件；
- 后端/Agent 逻辑：理解消息并决定要做什么；
- 回复与通知：发布版本提醒、测试结果或待办摘要；
- 权限控制：只申请实际需要的最小权限。

如果团队准备停用飞书，则无需继续开发这个智能体。确认所有资料已导出、所有权和权限已交接后，可以撤销应用授权，再按飞书的流程停用组织。
